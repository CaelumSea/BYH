## Overall verdict

**V3 is substantially stronger and close to implementation-ready.** It correctly incorporates nearly all major V2 review points: clean-room implementation, non-blocking sessions, best-effort clipboard preservation, native no-activation windows, composable provider architecture, UI-based custom actions, and an honest alpha/beta/release timeline. 

My verdict is **approved with seven required corrections**. Two are implementation blockers; the others should be fixed before Phase 1.

---

## 1. Selection capture still does not start immediately

The prose says capture begins immediately, concurrently with the anti-flicker delay. 

But the pseudocode does this:

1. Wait 60–100 ms.
2. Show toolbar.
3. Start `CaptureAsync`.

That means capture is still delayed. 

It should start the capture task first:

```csharp
public async Task StartOrReplaceSessionAsync(
    SelectionGesture gesture,
    CancellationToken sessionToken)
{
    // Capture begins immediately.
    Task<CaptureResult> captureTask =
        _capture.CaptureAsync(gesture, sessionToken);

    // Anti-flicker delay runs concurrently.
    Task delayTask = Task.Delay(AntiFlickerMs, sessionToken);

    await delayTask;

    await Dispatcher.UIThread.InvokeAsync(() =>
        ShowToolbar(gesture.MouseUpPosition));

    CaptureResult result = await captureTask;

    sessionToken.ThrowIfCancellationRequested();

    await Dispatcher.UIThread.InvokeAsync(() =>
        ToolbarSetCaptureResult(result));
}
```

The current pseudocode also calls `ShowToolbar` and `ToolbarSetText` inside `Task.Run`. Avalonia uses a single-threaded UI model; UI properties and controls must be accessed through the UI dispatcher, or Avalonia can throw an invalid-thread exception. ([Avalonia Docs][1])

Also add:

* `_currentCts?.Dispose()` after cancellation.
* A monotonically increasing `sessionId`.
* A final `sessionId == _currentSessionId` check before every UI update.
* Store the running task instead of using unobserved fire-and-forget `Task.Run`.

This protects against a capture implementation that returns a stale result despite cancellation.

## 2. The injected-event explanation is technically wrong

The document says simulated `Ctrl+C` would re-enter the `WH_MOUSE_LL` hook and trigger another selection. 

That cannot happen: `Ctrl+C` is keyboard input, while `WH_MOUSE_LL` receives mouse events. Microsoft documents `MSLLHOOKSTRUCT` and `LLMHF_INJECTED` specifically for injected **mouse** events. Keyboard-hook events use the separate `KBDLLHOOKSTRUCT` and `LLKHF_INJECTED` flag. ([Microsoft Learn][2])

There is also a symbol typo throughout the document:

```text
LLMH_INJECTED     // incorrect
LLMHF_INJECTED    // correct
```

Revise the rule to:

> Ignore mouse events generated by this application only if the application ever synthesizes mouse input. Simulated copy keystrokes do not re-enter `WH_MOUSE_LL`. If a low-level keyboard hook is later added, identify injected keyboard input through `LLKHF_INJECTED` and preferably an application-specific `dwExtraInfo` marker.

Do not discard every injected mouse event globally. Accessibility software, remote-control tools, automation software, and pen/touch translation layers may inject legitimate events. A safer design is:

```csharp
const nuint OurInputMarker = 0x53454C41; // example

bool IsOurInjectedMouseEvent(MSLLHOOKSTRUCT e) =>
    (e.flags & LLMHF_INJECTED) != 0 &&
    e.dwExtraInfo == OurInputMarker;
```

The current risk-table entry about synthetic copy re-triggering the mouse hook should therefore be removed or rewritten.

## 3. Fix the selection geometry and double-click identity

The current algorithm converts rectangular system metrics into a Euclidean-distance test:

```text
distance >= max(SM_CXDRAG, SM_CYDRAG)
```

That does not match Windows semantics. `SM_CXDOUBLECLK` and `SM_CYDOUBLECLK` describe a rectangle, and the drag metrics describe horizontal and vertical movement around the original point. ([Microsoft Learn][3])

Use axis-based tests:

```csharp
bool isDrag =
    Math.Abs(up.X - down.X) >= dragThresholdX ||
    Math.Abs(up.Y - down.Y) >= dragThresholdY;

bool isDoubleClick =
    elapsed <= doubleClickTime &&
    Math.Abs(up.X - lastUp.X) <= doubleClickWidth / 2 &&
    Math.Abs(up.Y - lastUp.Y) <= doubleClickHeight / 2 &&
    currentRootHwnd == lastRootHwnd &&
    currentPid == lastPid &&
    currentButton == lastButton;
```

The current code does not ensure that the previous click occurred in the same window or process. Two quick clicks in neighboring windows could otherwise be classified as a double-click.

Also revise:

```text
Thread priority: AboveNormal
```

to:

```text
Thread priority: Normal by default; change only after profiling demonstrates a need.
```

Microsoft requires the hook thread to have a message loop and recommends handing work to another thread quickly, but it does not require elevated thread priority. It also documents the hook timeout as registry-configured and capped at 1,000 ms on supported Windows versions; the specification should remove the unsupported “default ~300 ms” assertion. ([Microsoft Learn][4])

Finally, `Shift+click` should not bypass all window/context checks. Require at least:

* Same foreground/root process as the mouse-down.
* No toolbar already under the cursor.
* Capture success before showing a normal actionable toolbar.

## 4. Process policies cannot be a single enum

The policy model is a good improvement, but the proposed values are mutually exclusive. 

A PDF reader may need both:

* `CopyAllowed`
* `DelayedClipboardRead`

A terminal may need:

* `CopyWithCtrlInsertOnly`
* A custom stabilization duration
* Possibly `AccessibilityOnly` for one version but not another

Use a policy object rather than an enum:

```json
{
  "match": {
    "processName": "Acrobat.exe"
  },
  "detectionEnabled": true,
  "accessibilityCapture": true,
  "simulatedCopyMode": "CtrlInsertThenCtrlC",
  "clipboardStabilizationMs": 150,
  "manualFallback": true
}
```

Suggested model:

```csharp
public sealed record ProcessCapturePolicy(
    bool DetectionEnabled,
    bool AccessibilityEnabled,
    SimulatedCopyMode CopyMode,
    int ClipboardStabilizationMs,
    bool ManualFallbackEnabled);
```

Define matching precedence explicitly:

1. Exact executable path or macOS bundle identifier
2. Signed application identity, where available
3. Process name
4. Default policy

Otherwise user overrides can behave unpredictably when multiple rules match.

## 5. The clipboard state machine needs sequencing corrections

The best-effort wording and sequence-number restoration are now appropriately cautious. 

However, several details remain:

### `OpenClipboard` retry is placed in the wrong state

The plan puts `OpenClipboard` retry immediately before `SendInput`. `SendInput` itself does not open the clipboard. Retry logic is needed around:

* Snapshot reads
* Captured-text reads
* Restoration writes
* Clipboard clearing

Move bounded retry into a reusable clipboard-access function.

### Restoration will generate more update notifications

Before restoration:

* Unsubscribe the listener, or
* Mark the operation as being in `Restoring` state and ignore its own notifications.

Otherwise restoration can reset the stabilization timer or be mistaken for an external clipboard change.

### Cancellation must not leave modifier keys pressed

Send the complete keyboard chord in one `SendInput` array:

```text
Ctrl down
Insert/C down
Insert/C up
Ctrl up
```

Also inspect current modifier state before injection. Microsoft explicitly warns that keys already held by the user can interfere with `SendInput`. ([Microsoft Learn][5])

If Ctrl, Alt, Shift, Command, or another relevant modifier is currently held:

* Defer briefly, or
* Abandon automated capture and use manual fallback.

### macOS KVO should not yet be promised

The text says to use “KVO on `NSPasteboard.changeCount`.” That should remain a Phase 0 experiment, not an implementation commitment. Specify:

> Use a native change notification if verified on supported macOS versions; otherwise use bounded low-frequency polling of `changeCount`.

### Test more clipboard cases

Add integration tests for:

* Empty clipboard
* Text plus HTML/RTF
* Large image clipboard
* File list
* Delayed-rendered content
* Clipboard owner process exiting
* User copying during capture
* User copying during restoration
* Application writing three or more updates
* Capture cancellation after simulated input but before read
* Clipboard unavailable for the entire timeout

## 6. UI Automation timeout wording remains too strong

The specification says UIA calls have a strict timeout and are “aborted” after 500 ms. 

A `CancellationToken` or `Task.WhenAny` can stop waiting for a UIA/COM call, but it does not necessarily terminate the blocked native call itself. The implementation should distinguish:

* **Caller timeout:** the session stops waiting and proceeds to clipboard fallback.
* **Worker recovery:** the blocked UIA worker is quarantined or replaced.
* **Actual call cancellation:** generally not assumed.

Recommended architecture:

```text
One dedicated UIA worker
    ↓
Execute request with request ID
    ↓
Caller waits at most 300–500 ms
    ↓ timeout
Ignore eventual stale result
Mark worker unhealthy
Create replacement worker if necessary
```

Do the following operations on the same UIA worker:

1. Resolve focused element.
2. Resolve element at the mouse point.
3. Query `TextPattern2`/`TextPattern`.
4. Walk bounded parents.
5. Return plain text and metadata.

Avoid resolving an `AutomationElement` on one thread and then casually passing it into another execution context.

The acceptance test should include a deliberately broken or sleeping UIA provider to verify that the toolbar and other capture paths remain responsive.

## 7. macOS still needs a more explicit runtime strategy

The two-capability model is better than V2, and the signing/notarization work is now recognized. 

Add these decisions:

### Event-tap recovery

A global event tap can stop delivering events. The platform implementation needs:

* Detection of tap-disabled callback events.
* Re-enabling the tap where appropriate.
* A health watchdog.
* A user-visible degraded-state indicator if re-enabling fails.

### Distribution model

State explicitly:

> Initial macOS distribution is a notarized Developer ID application distributed outside the Mac App Store. The first release will not rely on App Sandbox compatibility.

This prevents a late conflict between global accessibility behavior and distribution assumptions.

### Stable identity

TCC/accessibility testing must use:

* A stable bundle identifier.
* A stable Developer ID signature.
* The actual packaged application path.
* Real upgrade installation, not only debug builds.

### Terminology

On Retina displays, macOS gesture thresholds and popup coordinates should be described in **points**, not “5 px.”

## Provider and configuration improvements

The raw HTTP provider design is appropriate, and the seven SSE cases are a solid start. 

Add the following:

### Secret custom headers

`customHeaders` may contain secrets such as gateway tokens, but the document promises no plaintext secrets. Support references:

```json
{
  "customHeaders": {
    "X-Tenant": {
      "value": "team-a",
      "isSecret": false
    },
    "X-Gateway-Key": {
      "secretReference": "secret://provider/local-gateway/header/X-Gateway-Key",
      "isSecret": true
    }
  }
}
```

### URL composition

Define exactly how these combine:

```text
baseUrl = https://gateway.example/company/openai/v1
chatCompletionsPath = chat/completions
```

Use URI-aware joining, not string concatenation, so `/v1` is not accidentally discarded.

### Redirect security

For authenticated requests:

* Disable redirects by default, or permit only same-origin redirects.
* Never forward secret custom headers to a different host.
* Do not expose a “disable TLS verification” option.

### AOT serialization

Use source-generated `System.Text.Json` contexts for configuration, requests, responses, and SSE payloads. Reflection-based serialization can undermine the stated NativeAOT design.

### Versioning

Add `schemaVersion` to `ProviderProfile`, settings, and process policies—not only actions—and define migration behavior.

## Metrics and acceptance criteria

The P95 target is useful, but it needs a measurement contract. 

Define toolbar latency as:

> Time from the operating-system mouse-up event timestamp to the first compositor-presented frame containing the toolbar.

Report separately:

* Cold process startup
* Warm but hidden application
* First toolbar display
* Subsequent toolbar displays
* 100%, 150%, and 200% scaling
* Intel and Apple Silicon macOS
* UIA-success and clipboard-fallback sessions

“Capture works” should also become measurable:

```text
Automatic capture success rate ≥ 95% over the supported-app test corpus
No incorrect text returned as a successful capture
Manual fallback succeeds in all remaining test cases
Zero clipboard-clobber failures in the concurrency stress suite
```

A toolbar should not present enabled actions when capture returns empty or ambiguous text. Show an explicit manual-copy state instead.

## Timeline correction

The timeline is now much more honest. 

One remaining mismatch: the public-release definition includes **updates**, but the phases do not include an updater architecture. Either:

* Add 3–5 days for signed update manifests, integrity verification, rollback/failure handling, and per-platform update behavior; or
* Remove automatic updates from the first public-release definition.

Also rename “single-file” packaging to:

> Platform-native self-contained distribution where feasible: Windows executable/installer and signed macOS application bundle.

A macOS `.app` is inherently a structured signed bundle, even when the managed executable is NativeAOT.
